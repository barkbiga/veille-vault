# LLM 0.32a0 is a major backwards-compatible refactor

| | |
|---|---|
| **Pertinence** | 4.0/5 |
| **Catégorie** | Architecture |
| **Source** | [Simon Willison](https://simonwillison.net/2026/Apr/29/llm/#atom-everything) |

## Résumé

Simon Willison refactorise sa bibliothèque LLM (abstraction multi-modèles) pour gérer **l'explosion des types d'entrée/sortie**. Pivot architectural : passage de `prompt → response text` à `messages[] → streaming parts[]`. Motivations : (1) **Messages as conversations** — permettre de réhydrater des conversations complètes (avant : uniquement build from scratch), (2) **Streaming parts** — gérer outputs hétérogènes (texte + reasoning + tool calls + images + tool outputs serveur-side). Nouveaux builders `llm.user()`, `llm.assistant()`. Pattern `response.reply()` pour continuer une conversation. **Backward compatible**. Cas d'usage : Claude peut retourner reasoning + texte + tool calls + résultats dans un seul stream. Abstraction critique pour gérer la **diversité croissante des modèles frontier**.

## Actions recommandées

- [ ] Analyser le pattern "messages as API contract" pour agents bancaires — analogie avec token introspection/context
- [ ] Étudier l'architecture "streaming parts" comme modèle pour responses composites (autorisation + métadonnées + reasoning)
- [ ] Évaluer l'impact sur NHI : si un agent retourne tool_call + reasoning + result, comment auditer la décision ?
- [ ] Considérer abstraction similaire pour Authorization Servers dédiés — gérer diversité FAPI/OAuth/OIDC/custom

## 📝 Notes personnelles

**Pattern architectural fort** : L'abstraction initiale (`prompt → text`) ne scale pas face à la diversité des modèles. **Leçon pour APIs bancaires** : les abstractions doivent anticiper l'évolution, pas juste le cas d'usage actuel.

**Lien agent identity** : Si un agent retourne `[reasoning, tool_call, tool_output, final_answer]`, quel élément audite-t-on ? Le reasoning est-il considéré comme "justification" au sens RGPD/explicabilité ?

**Trade-off intéressant** : Backward compatible MAIS abstraction radicalement différente. Difficile à faire — respect pour l'engineering.

**Streaming parts = composabilité** : Même logique que les microservices ou les event streams. Un output n'est plus monolithique mais un flux de parts typées. **Analogie OAuth** : token response pourrait inclure `[access_token, refresh_token, metadata, reasoning_context]` ?

**Question architecture** : Les Authorization Servers devraient-ils adopter le même pattern ? Actuellement, on retourne `{access_token, expires_in}`. Mais si un agent demande autorisation, ne devrait-on pas retourner `[decision, reasoning, constraints, token]` ?

**Signal faible** : La "conversational API" devient le standard de facto (OpenAI, Anthropic, Google...). Les APIs non-conversationnelles (REST classique) deviennent legacy ?
